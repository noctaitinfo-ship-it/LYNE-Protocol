The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT",
"RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as
described in BCP 14 [RFC 2119] [RFC 8174] when, and only when, they appear in all capitals.

## 1. Motivation

Relationships between a provider and a client — a repair, an appointment, a tenancy — are usually
coordinated through persistent personal addresses: phone numbers, e-mail addresses, messenger
identifiers. Whoever holds an address can reach its owner indefinitely, communication accumulates
as message history, and the current status of the underlying matter has to be reconstructed from
that history.

LYNE uses a different structure:

- The matter itself, the **Thing**, is the primary object. Its current **State** is explicit,
  versioned, hash-chained and signed.
- A client has no global address and no account. A client identity exists only inside one Thing
  (a **Thing-key**) and is created when the client redeems a **Grant** issued by the provider.
- Live communication is a temporary capability of the Thing, bounded by the Grant (purpose,
  channels, time window, number of uses). It is transient and never persistent (§2.5).
- The only persistent artifact of communication is a **Result**: a short outcome signed by both
  parties that moves the Thing to its next State.

LP 0.1 specifies the objects (Thing, State, Grant, Result), Redemption, Rendezvous, the Live Line,
Revocation and Expiry, and the lifecycle that connects them. It reuses published mechanisms (§13)
and claims no novelty for any individual mechanism; `02_Uuring/Prior_art/REMOVAL_TEST_v2.md`
records which composition remains after those mechanisms are subtracted.

## 2. Terminology

### 2.1 Roles and objects

- **Provider** — the party that creates Things and issues Grants for them (for example a clinic, a
  landlord, a contractor). Identified in LP 0.1 by an Ed25519 key, the *provider key*.
- **Client** — the counterparty of a Thing. Identified only by its Thing-key after Redemption.
- **Endpoint** — software acting for the Provider or for the Client, operated by a human or by a
  software agent (§14).
- **Thing** — a Provider-created, Provider-signed work object (§3).
- **State** — a signed, versioned, hash-chained record of a Thing's current status (§4).
- **Grant** — a Provider-signed, Thing-bound authorization that can be redeemed once and then
  authorizes a bounded number of Live Lines (§5).
- **Grant Secret (S)** — 32 bytes from a cryptographically secure random generator, delivered
  alongside a Grant but never inside it (§5.3).
- **Redemption** — the one-time procedure that binds a Client's Thing-key to a Thing (§6).
- **Thing-key** — an Ed25519 key pair generated by a Client endpoint for exactly one Thing.
- **Binding** — the Provider's record that a Thing-key is the Client key of a Thing.
- **Rendezvous Service** — a store-and-forward service where endpoints exchange encrypted
  signaling envelopes at derived addresses (§7).
- **Live Line** — a temporary WebRTC connection between the two endpoints of a Thing (§8).
- **Result** — the bilaterally signed outcome of one Live Line (§9).
- **Epoch** — a per-Thing revocation generation, an integer starting at 0 (§10.3).
- **Runtime component** — a Rendezvous Service or a TURN server.
- **Audit record** — Provider-side metadata about Grants and Bindings; never content.

### 2.2 Encoding

- Objects are JSON [RFC 8259] encoded in UTF-8. LP 0.1 objects contain only strings, integers,
  booleans, null, arrays and objects. Non-integer numbers MUST NOT appear. Member names are ASCII.
- *b64u* denotes base64url without padding [RFC 4648, §5].
- Identifiers (`thing_id`, `grant_id`, `result_id`, `challenge`) are 16 bytes from a
  cryptographically secure random generator, b64u-encoded (22 characters).
- Public keys are raw 32-byte Ed25519 public keys [RFC 8032], b64u-encoded (43 characters).
- A *kid* is the JWK Thumbprint [RFC 7638] with SHA-256 of the key's OKP JWK [RFC 8037],
  b64u-encoded (43 characters).
- Hashes are SHA-256, b64u-encoded (43 characters).
- Times are RFC 3339 [RFC 3339] UTC with the suffix `Z` and whole seconds, for example
  `2026-09-28T10:00:00Z`.
- The canonical form of an object is its JCS serialization [RFC 8785].
- Every object carries `"lp_version": "0.1"`. A receiver MUST reject an object with an
  unsupported `lp_version` (error `VERSION_UNSUPPORTED`).

### 2.3 Signatures

Signatures are detached JWS [RFC 7515, Appendix F] with algorithm `EdDSA` [RFC 8037]:

1. JWS Protected Header: exactly `{"alg":"EdDSA","kid":<kid of the signing key>}`, serialized
   with JCS.
2. JWS Payload: the JCS serialization of the object with its signature member(s) removed. The
   signature member is `signature` for Thing, State, Grant, Redemption statement and Redemption
   Receipt; for a Result both `provider_sig` and `client_thing_sig` are removed, so both parties
   sign the identical payload.
3. Signature member value: `BASE64URL(header) || ".." || BASE64URL(signature)` (payload omitted).
4. A verifier MUST reconstruct the payload from the received object, MUST check that `kid` equals
   the kid of the key expected for the signer's role (§3–§9), and MUST reject any additional
   header parameter.

### 2.5 Persistence terms

Every storage obligation in this document uses exactly one of the following terms.

| Term | Meaning |
|---|---|
| persistent | Kept in durable storage with no protocol-defined end; deleted only under the holder's own retention policy |
| retained until *event* | Kept until the named event, then deleted by the holder |
| transient | Held only for a bounded period — one operation, one Live Line, or a stated TTL — and deleted when it ends; never included in backups, logs or analytics |
| not held | Never received, or discarded on receipt without being stored |

"MUST NOT be persisted" means that the data is at most transient.

### 2.6 Cryptographic profile

LP 0.1 uses standard primitives only and defines no custom cryptography. The canonical LP 0.1 core
profile is exactly:

| Primitive | Specification | Used for |
|---|---|---|
| Ed25519 / EdDSA | RFC 8032, RFC 8037 | Provider keys, Thing-keys, every LP signature (§2.3) |
| SHA-256 | FIPS 180-4 | State hashes, `secret_commitment`, kid (JWK Thumbprint), inside HMAC and HKDF |
| HMAC-SHA256 | RFC 2104 | `secret_proof` (§6.2) |
| HKDF-SHA256 | RFC 5869 | `K_redeem`, `PRK_line`, rendezvous addresses, `K_signal` (§6.2, §7.2) |
| AES-256-GCM | NIST SP 800-38D | Signaling envelopes (§7.3) |
| JCS | RFC 8785 | Canonical form of signed objects (§2.2) |
| Detached JWS | RFC 7515 | Signature format (§2.3) |
| HTTP Message Signatures | RFC 9421 | Thing endpoint requests (§6.5) |
| WebRTC | RFC 8825, RFC 8827, RFC 8829 | Live Line (§8) |
| ICE | RFC 8445 | Live Line connectivity |
| STUN | RFC 8489 | Live Line connectivity |
| TURN | RFC 8656 | Live Line relay (§8.6) |
| DTLS-SRTP | RFC 5763, RFC 5764 | Media protection |
| SCTP/DTLS data channels | RFC 8831, RFC 8832 | `lyne-control`, `lyne-data` (§8.3) |

1. An implementation MUST NOT replace, add or combine primitives outside this profile for any LP 0.1
   object, derivation or message.
2. WebAuthn is not an LP 0.1 wire primitive. A product MAY use it to authenticate people to a
   Provider Console; no LP 0.1 object, derivation or message depends on it.
3. X25519 is not used directly by LP 0.1 and is not a required core primitive. The key exchange
   inside the DTLS handshake is negotiated by the WebRTC stack as part of DTLS-SRTP and is not an
   LP-defined primitive.
4. Every random value in LP 0.1 — identifiers, S, `line_salt`, challenges, AES-GCM nonces and key
   pairs — comes from a cryptographically secure random generator.

## 3. Thing

### 3.1 Fields

| Field | Type | Rule |
|---|---|---|
| `lp_version` | string | `"0.1"` |
| `thing_id` | id | Random; assigned by the Provider; MUST NOT be reused |
| `type` | string | Provider-defined token `^[a-z0-9][a-z0-9._-]{0,63}$`, e.g. `repair.plumbing` |
| `title` | string | 1–140 characters; the label both parties see |
| `provider_pub` | public key | The Provider's key; signs this Thing |
| `created_at` | time | Creation time |
| `closed_at` | time or null | Null in every revision except the closing revision |
| `version` | integer ≥ 1 | Revision number of the Thing record |
| `signature` | detached JWS | By `provider_pub` |

Schema: `Schemas/thing.schema.json`.

### 3.2 Rules

1. A Thing is created and signed by its Provider. The Thing is first-class: every State, Grant,
   Binding, Live Line and Result belongs to exactly one Thing.
2. A change of `type`, `title` or `closed_at` creates a new revision with `version` + 1, signed by
   the Provider. `thing_id`, `provider_pub` and `created_at` MUST NOT change between revisions.
3. `closed_at` is null in every revision except the closing revision. After the closing revision
   the Thing is terminal: no further revision, State, Grant, Redemption, Live Line or Result is
   accepted (error `THING_CLOSED`).
4. The Thing is persistent at the Provider and, after Redemption, at the Client endpoint. It is not
   held by runtime components.
5. A Client endpoint MUST pin `provider_pub` per `thing_id` at the first Redemption and MUST reject
   any later object for the same `thing_id` signed by a different provider key (error
   `KEY_MISMATCH`). LP 0.1 has no Provider key rotation: the provider key of a Thing never
   changes. A compromised provider key freezes or revokes the affected Thing relationships, and a new
   provider key requires a newly established trusted relationship, that is, a new Thing (§10 item 8).
6. `title` SHOULD contain no more personal data than the parties need to recognize the Thing.

## 4. State

### 4.1 Fields

| Field | Type | Rule |
|---|---|---|
| `lp_version` | string | `"0.1"` |
| `thing_id` | id | The Thing |
| `version` | integer ≥ 1 | 1 for the first State, then + 1 per transition |
| `prev_state_hash` | hash or null | Null iff `version` = 1; otherwise SHA-256 of the JCS of the complete previous State, including its signature |
| `status` | enum | `OPEN`, `WAITING`, `CLOSED` |
| `waiting_on` | enum or null | `provider` or `client` iff `status` = `WAITING`; otherwise null |
| `next_action` | string or null | 1–140 characters; non-null when `WAITING`; null when `CLOSED` |
| `deadline` | time or null | Optional time bound for `next_action`; null when `CLOSED` |
| `actor` | enum | `provider` or `client`: the role whose key signed this State |
| `result_id` | id or null | The anchoring Result (§9.5); null for `version` 1 and for transitions not caused by a Result |
| `timestamp` | time | Time of the transition |
| `signature` | detached JWS | By the actor's key: provider key or bound Thing-key |

Schema: `Schemas/state.schema.json`.

### 4.2 Status values and lifecycle phases

The persistent status of a Thing is one of:

- `OPEN` — the Thing is active and no party is specifically awaited.
- `WAITING` — an action described by `next_action` is expected from the party named in
  `waiting_on`, optionally before `deadline`.
- `CLOSED` — terminal.

The conceptual lifecycle also contains the phases LIVE and RESULT. LIVE and RESULT are lifecycle
phases, not State values: a Live Line is ephemeral by definition (§8.5) and a complete Result is
itself the persistent artifact of the RESULT phase (§9.6). Recording either phase as State would
persist something ephemeral or duplicate the Result. The user-interface label "LYNE" denotes the
LIVE phase and does not appear in the wire format. §15.2 maps every phase to its representation.

### 4.3 Rules

1. The Provider creates State `version` 1 together with the Thing (`actor` = `provider`,
   `prev_state_hash` = null, `result_id` = null).
2. Each later State has `version` = previous `version` + 1 and `prev_state_hash` = SHA-256 of the
   JCS of the complete previous State.
3. Transition rights. A Provider MAY make any transition that does not start from `CLOSED`. A
   Client MAY propose transitions between `OPEN` and `WAITING` (for example returning the action to
   the Provider). A Client MUST NOT set `CLOSED` except through a Result (§9).
4. A State with a non-null `result_id` MUST be the transition anchored by that Result (§9.5).
5. Ordering authority. The Provider serializes the State chain. A proposed State is accepted only
   if its `version` equals the current `version` + 1, its `prev_state_hash` matches, its signature
   verifies against the actor's key, and rule 3 permits the transition. Otherwise the Provider
   rejects it with `STATE_CONFLICT` and returns the current State (optimistic concurrency).
6. Exchange. State is exchanged over the Provider's Thing endpoint (§6.5) or over the
   `lyne-control` channel of a Live Line (§8.3). LP 0.1 defines no push channel; a Provider MAY use
   a content-free change signal (no `thing_id`, no State content) on a channel the Client endpoint
   opted into outside LP 0.1.
7. Persistence. The State chain is persistent at the Provider, which holds the authoritative chain.
   At the Client endpoint the latest verified State is persistent; the full chain MAY be. State is
   not held by runtime components.

## 5. Grant

### 5.1 Fields

| Field | Type | Rule |
|---|---|---|
| `lp_version` | string | `"0.1"` |
| `grant_id` | id | Random; also the replay discriminator (A2R `jti`) |
| `thing_id` | id | The Thing the Grant is bound to |
| `issuer` | public key | MUST equal the Thing's `provider_pub` |
| `subject` | string | `"client"` in LP 0.1: the role conferred on the redeemer |
| `aud` | https origin | `^https://[a-z0-9.-]+(:[0-9]{1,5})?$`; where the Grant is fetched and redeemed |
| `purpose` | token | Opaque, Provider-defined `^[A-Za-z0-9._:-]{1,64}$`; MUST NOT contain personal data |
| `channels` | array | Non-empty set of `voice`, `video`, `data` |
| `issued_at` | time | Issuance; start of the bearer phase |
| `redeem_by` | time | End of the bearer phase: Redemption is accepted only before `redeem_by` (§5.3 rule 4) |
| `not_before` | time | Earliest Live Line |
| `exp` | time | End of Live Line authority |
| `line_max_seconds` | integer 60–86 400 | Maximum duration of each Live Line (the master plan's `window`) |
| `max_uses` | integer ≥ 1 | Number of Live Lines authorized after Redemption |
| `epoch` | integer ≥ 0 | The Thing's epoch at issuance (§10.3) |
| `secret_commitment` | hash | b64u(SHA-256(S)) |
| `signature` | detached JWS | By `issuer` |

Schema: `Schemas/grant.schema.json`.

### 5.2 Relationship to A2R

The Grant adapts the candidate authorization object of the A2R draft
(`draft-das-6g-query-scoped-communication-handles-06`, §9 "Authorization Object (Informative
Sketch)"). The fields are not LYNE inventions.

| A2R candidate field | LP 0.1 | Note |
|---|---|---|
| `grant_id` | `grant_id` | Same role |
| `from` | the bound Thing-key | Unknown at issuance; fixed at Redemption (sender binding) |
| `to` | `issuer` for `thing_id` | The Provider is reached in the context of the Thing |
| `purpose` | `purpose` together with `thing_id` | The Thing is the context; `purpose` stays opaque |
| `channel` | `channels` | A set instead of a single value |
| `exp` | `exp` (with `issued_at`, `redeem_by`, `not_before`) | The bearer phase ends at `redeem_by` |
| `max_attempts` | `max_uses` | Counts Live Lines |
| `epoch` | `epoch` | Scoped to one Thing |
| `jti` / `nonce` | `grant_id`; per-attempt `challenge` (§6.2) | |
| `aud` | `aud` | https origin of the Provider's LYNE endpoint |

### 5.3 Rules

1. Issuance. Only the Provider issues Grants, from its own backend, for one of its own Things. A
   public web control, such as a button or link on a provider page, is not a Grant: it can only
   carry an opaque reference that the Provider resolves in an authenticated context of its own
   (master plan, work package AB).
2. Grant Secret. S MUST NOT appear inside the Grant object. The Grant carries only
   `secret_commitment` = b64u(SHA-256(S)).
3. Delivery. A Grant is delivered as the link `https://<aud host>/l/<grant_id>#<b64u(S)>`; a QR
   code encodes the same link. The fragment keeps S out of HTTP requests and server logs. The
   Provider SHOULD deliver the link through its existing relationship with the Client (in person,
   its own portal, its own existing correspondence). LP 0.1 defines no delivery channel. Handling of
   the fragment is governed by §5.4.
4. Time. `issued_at` < `redeem_by` ≤ `issued_at` + `REDEEM_WINDOW_MAX`, and `redeem_by` ≤ `exp`;
   `issued_at` ≤ `not_before` < `exp`. `exp` − `issued_at` SHOULD NOT exceed `GRANT_MAX_LIFETIME`.
   `line_max_seconds` MUST NOT exceed `exp` − `not_before`. A Provider MUST NOT issue a Grant that
   violates these relations and a Client endpoint MUST reject one. JSON Schema cannot express these
   relations; `tests/run_tests.py` checks them.
5. Bearer phase and binding. The bearer phase is [`issued_at`, `redeem_by`), at most
   `REDEEM_WINDOW_MAX` (15 minutes). Within it, possession of the link (grant_id and S) is enough to
   redeem; after `redeem_by` an unredeemed Grant can no longer be redeemed (error
   `GRANT_REDEMPTION_EXPIRED`). Redemption binds the Grant to the Client's Thing-key. Afterwards the Grant
   authorizes Live Lines only for that key (sender binding) and cannot be redeemed again (error
   `GRANT_CONSUMED`). Because the bearer phase is short, a Provider SHOULD issue a Grant at the moment
   the Client needs it — for example when the Client, signed in to the Provider's own page, activates
   OPEN LYNE — rather than in advance.
6. Uses. `max_uses` is the number of Live Lines authorized after Redemption. Providers SHOULD issue
   `max_uses` = 1 in LP 0.1.
7. `subject` is `"client"` in LP 0.1: the Grant confers the Client role of `thing_id` on its
   redeemer.
8. `aud` is the https origin of the Provider's LYNE endpoint. A Client endpoint MUST fetch the Grant
   from, and redeem it only at, that origin.
9. Provider-side lifecycle of a Grant: `ISSUED` → `REDEEMED` → `EXHAUSTED` (all uses spent). An
   `ISSUED` Grant becomes `EXPIRED` at `redeem_by`; a `REDEEMED` Grant becomes `EXPIRED` at `exp`.
   Any Grant can become `REVOKED` (§10). Only an `ISSUED` Grant can be redeemed. Only a `REDEEMED`
   Grant with uses remaining can open a Live Line.
10. Audit. The Provider keeps an audit record per Grant: `grant_id`, `thing_id`, issuer kid, client
    kid (after Redemption), `issued_at`, `redeemed_at`, `revoked_at`, `exhausted_at`, uses. The
    audit record is persistent and MUST NOT contain S, `line_salt`, `PRK_line` or communication
    content.

### 5.4 Fragment secret cleanup

1. The redemption page served from `aud` at `/l/<grant_id>` MUST read S from the URL fragment once,
   as the first action of its own script, and MUST immediately remove the fragment from the address
   bar and from the session history (`history.replaceState`) — before it makes any request other
   than FetchGrant, Challenge and Redeem, and before it renders anything else.
2. The redemption page MUST NOT load third-party scripts, frames, fonts or analytics. It MUST be
   served with a Content-Security-Policy that limits scripts to its own origin and with
   `Referrer-Policy: no-referrer`.
3. Memory only. S and `line_salt` are volatile capability secrets. In a browser endpoint in LP 0.1
   they exist only in the memory of the running page and MUST NOT be persisted. In particular S and
   `line_salt` MUST NOT be written to: `localStorage`; `sessionStorage`; IndexedDB; the Cache API;
   service-worker caches; cookies; logs; analytics; crash telemetry; the URL query or path. The same
   applies to `PRK_line` and to every key derived from it (§7.2). At both parties S is retained
   until Redemption completes or `redeem_by` passes, whichever comes first.
4. Loss. If the page, tab or process that holds these secrets ends, the capability they carry is
   lost: without S the Grant can no longer be redeemed, and without `line_salt` or `PRK_line` no Live
   Line can be signalled under that Grant. LP 0.1 has no recovery, export, backup or account
   mechanism for them. If needed, the Provider issues a new Grant through its own relationship with
   the Client; an endpoint that still holds the bound Thing-key redeems it without creating a new
   identity (§6.4 rule 2).
5. The Thing-key is not a capability secret. A browser endpoint MAY keep its non-extractable
   Thing-key (§6.1), for example as a CryptoKey object in IndexedDB, because it is the Client's
   persistent identity for the Thing and cannot be exported. Rules 3 and 4 do not apply to it.
6. After a successful Redemption both parties compute `PRK_line = HKDF-Extract(salt = line_salt,
   IKM = S)` [RFC 5869], MUST delete S, and keep only `PRK_line` for the derivations of §7.
   `PRK_line` is retained until `exp`, in a browser endpoint in page memory only (rule 3).
7. On a final Redemption failure (`GRANT_CONSUMED`, `GRANT_REVOKED`, `GRANT_EXPIRED`,
   `GRANT_REDEMPTION_EXPIRED`, `THING_CLOSED`) the Client endpoint MUST delete S at once. After a
   transient failure, such as a network error, it MAY retain S in page memory until `redeem_by` in
   order to retry.
8. The Provider generates S and therefore knows it. It MUST NOT log S or the delivery link, and MUST
   delete S when the Redemption succeeds or at `redeem_by`. The Provider holds S, `line_salt` and
   `PRK_line` only as transient data (§15.3), never in logs, analytics, crash telemetry or audit
   records; a Provider endpoint that runs in a browser follows rule 3. A Provider that hands the link
   to a system that logs it (for example its own outbound correspondence) SHOULD issue the Grant only
   on demand, so that any logged copy of the link is already consumed or expired.
9. Copies outside the endpoints' control — camera or QR-scanner history, screenshots, a photographed
   code — remain possible. They are bounded by `REDEEM_WINDOW_MAX` and by one-time Redemption
   (`Threat_model.md`, T21).

## 6. Redemption and Thing-bound Identity

### 6.1 Thing-key

1. A Client endpoint generates an Ed25519 key pair for exactly one Thing. The private key MUST NOT
   leave the endpoint; browser endpoints MUST create it as a non-extractable Web Cryptography key.
2. A Client endpoint MUST NOT use one Thing-key for two Things, so that Client identities are not
   linkable across Things through LYNE identifiers.
3. If the endpoint already holds a bound Thing-key for `thing_id`, it MUST reuse that key
   (continuity).

### 6.2 Procedure

1. Fetch and verify. The Client endpoint opens the link, takes S from the fragment and removes the
   fragment (§5.4), fetches the Grant from `aud` over HTTPS and verifies: `lp_version`; the
   signature by `issuer`; SHA-256(S) = `secret_commitment`; the time relations of §5.3 rule 4;
   current time < `redeem_by` + `MAX_CLOCK_SKEW` (otherwise `GRANT_REDEMPTION_EXPIRED`); the
   origin it fetched from equals `aud`; and, if a provider key is pinned for `thing_id`, that it equals
   `issuer`.
2. Key. The endpoint obtains the existing Thing-key for `thing_id` or generates one (§6.1).
3. Challenge. The endpoint requests a challenge. The Provider returns `challenge` (16 random bytes,
   b64u), bound to `grant_id`, valid for `CHALLENGE_TTL` and usable once.
4. Proof. The endpoint computes
   `K_redeem = HKDF-SHA256(IKM = S, salt = none, info = "LYNE/0.1/redeem", L = 32)` [RFC 5869] and
   `secret_proof = b64u(HMAC-SHA256(K_redeem, JCS({"challenge", "client_thing_pub", "grant_id"})))`
   [RFC 2104]. S itself never leaves the endpoint.
5. Statement. The endpoint sends the Redemption statement (§6.3), signed with the Thing-key.
6. Verification. The Provider MUST verify all of: the Grant exists, was signed by its own key and
   is `ISSUED`; the Grant `epoch` equals the Thing's current epoch; the Thing is not closed; current
   time is in [`issued_at`, `redeem_by`) by the Provider's clock; the challenge is known,
   unexpired, unused and bound to this `grant_id`; `secret_proof` is correct (constant-time
   comparison); the statement signature verifies with `client_thing_pub`; and the binding rules
   of §6.4 allow the key.
7. Atomic consumption. The Provider MUST perform the transition `ISSUED` → `REDEEMED` and the
   recording of the Binding as one atomic compare-and-set keyed by `grant_id`. The challenge MUST be
   marked used before or within the same step. Exactly one Redemption per Grant can succeed; every
   concurrent or later attempt receives `GRANT_CONSUMED` and causes no state change.
8. Response. On success the Provider returns: the Redemption Receipt (§6.3); the current Thing;
   the latest State (and the State chain on request); existing Results; `line_salt`; the
   Rendezvous Service URL; and, if offered, short-lived TURN credentials (§8.6). `line_salt` is 16
   random bytes (b64u), confidential, returned only in this response, and MUST NOT be logged or
   entered in audit records. Both parties then replace S with `PRK_line` (§5.4 rule 6).
9. Failure. On any failure no Binding is recorded and the Grant status does not change. Errors are
   listed in §15.4. The Provider SHOULD rate-limit challenge and Redemption requests per
   `grant_id` and per source.
10. Replay. A captured Redemption statement cannot be replayed: its challenge is single-use and the
    Grant is no longer `ISSUED`. Opening the link after Redemption yields `GRANT_CONSUMED`.

### 6.3 Redemption statement and Redemption Receipt

Redemption statement (Client → Provider):

| Field | Rule |
|---|---|
| `lp_version` | `"0.1"` |
| `grant_id` | The Grant being redeemed |
| `thing_id` | MUST equal the Grant's `thing_id` |
| `client_thing_pub` | The Thing-key public key |
| `challenge` | As issued in step 3 |
| `secret_proof` | As computed in step 4 |
| `signature` | Detached JWS by `client_thing_pub` |

Redemption Receipt (Provider → Client, also the shape of the Binding audit record):

| Field | Rule |
|---|---|
| `lp_version` | `"0.1"` |
| `grant_id` | The redeemed Grant |
| `thing_id` | The Thing |
| `client_kid` | kid of `client_thing_pub` |
| `bound_at` | Time of the Binding |
| `uses_remaining` | Live Lines still authorized by this Grant |
| `signature` | Detached JWS by the provider key |

Examples: `examples/valid/redemption.json`, `examples/valid/redemption_receipt.json`.

### 6.4 Binding rules

1. The Thing has no bound Client key: the Provider binds `client_thing_pub`.
2. The bound key equals `client_thing_pub`: continuity; no new identity is created.
3. A different key is bound: the Provider rejects the Redemption with `BINDING_CONFLICT`. Rebinding
   requires the Provider to revoke the existing Binding first (§10.4).

### 6.5 Thing endpoint

1. The Provider exposes, at the `aud` origin, an HTTPS endpoint for each Thing. Roles over HTTP are
   fixed: the Client endpoint is always the requester and the Provider is always the responder. The
   Provider never calls the Client endpoint over HTTP; everything it offers the Client — State,
   Result proposals — is returned in responses to Client requests. Every Client request MUST be
   signed with the Thing-key using HTTP Message Signatures [RFC 9421], algorithm `ed25519`, covering
   at least `@method`, `@target-uri`, the `created` parameter and, when a body is present,
   `content-digest` [RFC 9530].
2. The Provider MUST reject a signature whose `created` is older than `HTTP_SIG_MAX_AGE` or later
   than the current time + `MAX_CLOCK_SKEW`, and MUST reject a repeated (`created`, signature) pair
   within that window.
3. Operations: *GetThing* (Thing, latest State, Results, `uses_remaining` of the current Grant, and
   `pending_result` — an open Provider-proposed Result that carries only `provider_sig`),
   *ProposeState* (§4.3 rule 5), *SubmitResult* (§9.3 rule 2).
4. Access is authorized by the Binding, not by a Grant: a bound Client MAY read its Thing and
   propose States for the life of the Thing until the Binding is revoked. Grants bound only Live
   Lines.

### 6.6 What the identity is, and is not

The Client is known to the Provider only by the kid of its Thing-key, within one Thing. What the
Provider knows about the person or organization behind that key comes from the Provider's own
relationship, in which it delivered the link, not from LYNE. LP 0.1 defines no account, profile,
directory, contact list or cross-Thing identifier.

## 7. Rendezvous

### 7.1 Purpose

Two endpoints that share S and `line_salt` meet without addresses to exchange WebRTC signaling.
The mechanism follows the shared-seed, time-derived rendezvous pattern documented by Berty/Wesh
(§13).

### 7.2 Derivation

1. `bucket` = floor(unix_seconds / `RDV_BUCKET`), written in decimal.
2. `line_seq` identifies the Live Line within a Grant: 1 … `max_uses`. The next `line_seq` is
   `max_uses` − `uses_remaining` + 1, as reported by the Provider.
3. `dir` names the direction of a signaling flow: `p2c` from the Provider endpoint to the Client
   endpoint, `c2p` from the Client endpoint to the Provider endpoint.
4. `PRK_line = HKDF-Extract(salt = line_salt, IKM = S)` (§5.4 rule 6).
5. `addr(dir, bucket) = b64u(HKDF-Expand(PRK_line, info = "LYNE/0.1/rdv|" dir "|" thing_id "|" epoch "|" line_seq "|" bucket, L = 32))`.
6. `K_signal(dir) = HKDF-Expand(PRK_line, info = "LYNE/0.1/signal|" dir "|" thing_id "|" epoch "|" line_seq, L = 32)`.
   The two directional signaling keys are `K_signal_p2c` = `K_signal(p2c)` and `K_signal_c2p` =
   `K_signal(c2p)`. Each is an AES-256-GCM key (§7.3).
7. Each endpoint publishes only in its outbound direction (Provider: `p2c`, encrypting with
   `K_signal_p2c`; Client: `c2p`, encrypting with `K_signal_c2p`) and reads only its inbound
   direction with the inbound key. A party therefore never accepts its own envelopes (a reflected
   envelope fails decryption), each direction has its own key and therefore its own AES-GCM nonce
   space (§7.3), and the direction whose key decrypted a signal message fixes the expected `from`.
8. Because `line_salt` is known only to the Provider and the redeeming Client, a party that holds
   only the delivery link cannot derive rendezvous addresses or signaling keys after Redemption.
9. An endpoint MUST publish to `addr(dir_out, bucket_now)` and MUST read `addr(dir_in, bucket_now − 1)`,
   `addr(dir_in, bucket_now)` and `addr(dir_in, bucket_now + 1)`.

Test vectors: `examples/valid/vectors.json`.

### 7.3 Envelopes and signal messages

1. Envelope: `{"addr": addr, "n": b64u(n), "c": b64u(AES-256-GCM(K_signal(dir), n, plaintext, aad = UTF-8(addr)))}`
   [NIST SP 800-38D], where `addr` and `K_signal` belong to the sender's outbound direction and `c`
   is the ciphertext followed by the 128-bit authentication tag.
2. Nonce. `n` is exactly 96 random bits (12 bytes), drawn from a cryptographically secure random
   generator for every envelope. A sender MUST NOT reuse a nonce under the same directional key.
   `K_signal_p2c` and `K_signal_c2p` are different keys and therefore have separate nonce spaces:
   the same nonce value under the opposite directional key is not a reuse.
3. Nonce-replay set. A receiver MUST keep, for the active Line (one `line_seq`), the set of nonces
   of the envelopes it has authenticated under its inbound key, and MUST reject an envelope whose
   nonce is already in that set, before decrypting it. A repeated fetch of the same envelope from
   the Rendezvous Service is rejected in the same way and is not an error. A nonce enters the set
   only after its envelope has authenticated (the AES-GCM tag verifies), so a forged envelope cannot
   block a genuine one. The set is transient and held in memory only: it is deleted when the Line
   ends (§8.4), or at `exp` if the signaling never led to a Line.
4. Plaintext: a signal message with the members `lp_version`, `thing_id`, `line_seq`, `seq`
   (per sender, starting at 1, strictly increasing), `from` (`provider` or `client`), `kind`
   (`offer`, `answer`, `ice` or `bye`), `body` (SDP, ICE candidate, or bye reason code),
   `sent_at` (time) and `signature` (detached JWS by the sender's key: provider key or bound
   Thing-key).
5. A receiver MUST decrypt with the inbound `K_signal(dir_in)` and with the address it read from as
   AAD, MUST reject an envelope whose `n` is not exactly 12 bytes or that fails authentication (a
   modified ciphertext, a modified address or the wrong directional key), MUST reject a message
   whose `from` does not match that direction (`p2c` requires `provider`, `c2p` requires `client`),
   MUST verify the signature against the expected key for `from`, and MUST reject a message whose
   `seq` does not increase or whose `sent_at` differs from its clock by more than `MAX_CLOCK_SKEW`.
6. Because every SDP is signed by a LYNE key, the DTLS certificate fingerprints it carries are
   authenticated end to end; neither the Rendezvous Service nor a TURN server can substitute them
   (the WebRTC security architecture [RFC 8827] relies on this signaling integrity).

Test vectors: `examples/valid/signal.json` (a signed `p2c` offer and `c2p` answer with their
envelopes).

### 7.4 Rendezvous Service obligations and visibility

1. Envelopes are transient at the Rendezvous Service: retained until `RDV_TTL` has passed.
2. It MUST NOT offer listing or enumeration; retrieval requires the exact `addr`.
3. Source network addresses and `addr` values are transient there (at most `RDV_TTL`); aggregate
   counters without identifiers MAY be persistent.
4. It SHOULD rate-limit per source.
5. It necessarily observes `addr` values (pseudorandom, rotating per bucket and separate per
   direction), envelope sizes, timing and source network addresses. It cannot observe S,
   `line_salt`, `PRK_line`, SDP, keys, identities or Thing content.

## 8. Live Line

### 8.1 Transport

WebRTC [RFC 8825] [RFC 8829] with the WebRTC security architecture [RFC 8827]; ICE [RFC 8445];
STUN [RFC 8489]; TURN [RFC 8656]; media protected with DTLS-SRTP [RFC 5763] [RFC 5764]; data
channels over SCTP/DTLS [RFC 8831] [RFC 8832].

### 8.2 Authorization to open

1. The Provider endpoint MUST accept an offer, or send one, only if: the Grant is `REDEEMED` with
   `uses_remaining` ≥ 1; the counterparty key is the bound Thing-key; current time is in
   [`not_before`, `exp`); the offered media and channels are within `channels`; the Grant `epoch`
   is current; and the Thing is not closed.
2. Accepting a new `line_seq` consumes one use in the same atomic step; a `line_seq` is never
   accepted twice.
3. Either endpoint MAY send the first offer. On glare the Provider's offer wins; the Client endpoint
   acts as the polite peer and answers.

### 8.3 Channels

1. `voice` means audio tracks; `video` means video tracks; `data` means one data channel labelled
   `lyne-data` for ephemeral content, such as an image shown during the Line.
2. Every Live Line also has one data channel labelled `lyne-control`. It carries only the protocol
   objects defined in this document (State proposals, Result proposals and countersignatures,
   `bye`); those objects follow their own persistence rules (§4.3, §9.6).
3. An endpoint MUST NOT offer or open media or data channels outside the Grant's `channels`. The
   Provider endpoint MUST end the Line if it observes one (error `CHANNEL_NOT_GRANTED`).

### 8.4 End of a Line

A Live Line ends at the earliest of: start + `line_max_seconds`; `exp`; a signed `bye` from either
endpoint; revocation (§10.2); ICE or media failure (`MEDIA_FAILED`).

### 8.5 Non-persistence

1. Line content — media and `lyne-data` payloads — is transient at both endpoints for the duration
   of the Line and MUST NOT be persisted by any party.
2. Line content is not held by the Rendezvous Service. A TURN server holds it only as transient,
   encrypted DTLS-SRTP and DTLS-protected SCTP packets that it relays and cannot decrypt.
3. The LIVE phase is not recorded in State.
4. LP 0.1 cannot technically prevent a participant from recording a Line by external means. This
   is a residual risk (`Threat_model.md`, T19).

### 8.6 TURN

TURN credentials MUST be short-lived (not valid beyond `exp`) and scoped to the Provider. A TURN
server observes network addresses, timing and volume of relayed Lines, but not content. This
metadata is transient: retained until the TURN allocation ends, and never linked to Thing, Grant or
key identifiers.

## 9. Result

### 9.1 Fields

| Field | Type | Rule |
|---|---|---|
| `lp_version` | string | `"0.1"` |
| `result_id` | id | Random; chosen by the proposing party |
| `thing_id` | id | The Thing |
| `grant_id` | id | The Grant under which the Line ran |
| `line_seq` | integer ≥ 1 | The Line this Result concludes |
| `outcome` | enum | `agreed`, `declined`, `deferred` |
| `summary` | string | 1–280 characters: the agreed outcome |
| `next_state` | object | `status`, `waiting_on`, `next_action`, `deadline`, with the constraints of §4.1 |
| `timestamp` | time | Time of the proposal |
| `provider_sig` | detached JWS | By the provider key |
| `client_thing_sig` | detached JWS | By the bound Thing-key |

Schema: `Schemas/result.schema.json`.

### 9.2 Meaning

A Result records the agreed outcome of one Live Line in at most 280 characters and names the
Thing's next State. It is not a record of the conversation.

### 9.3 Exchange

1. Over `lyne-control`, either party proposes a Result by filling its own signature member; the
   other party verifies the proposal and either countersigns the identical payload or declines.
2. Over the Thing endpoint the HTTP roles are fixed (§6.5 rule 1):
   - A Provider-proposed Result is offered as `pending_result` in GetThing responses until
     `RESULT_WINDOW` ends. The Client endpoint countersigns it and returns the complete Result with
     SubmitResult.
   - A Client-proposed Result is sent with SubmitResult carrying only `client_thing_sig`. The
     Provider countersigns or declines and answers with the complete Result or `RESULT_UNSIGNED`; if
     its decision is not immediate, the Client endpoint obtains it through GetThing.
3. The exchange ends no later than `RESULT_WINDOW` after the Line ended.
4. Both signatures cover the same JWS payload: the Result without `provider_sig` and
   `client_thing_sig` (§2.3).

### 9.4 Completeness

1. A Result is complete only with both valid signatures.
2. An incomplete Result (a proposal) MUST NOT change State. It is retained until it is
   countersigned, declined or `RESULT_WINDOW` ends, and is then deleted by both parties (error
   `RESULT_UNSIGNED` if it was not countersigned).
3. At most one complete Result exists per (`grant_id`, `line_seq`).

### 9.5 Anchoring

1. After a complete Result, the Provider MUST append exactly one State with `result_id` = the
   Result's `result_id`, `version` = current + 1, `status`, `waiting_on`, `next_action` and
   `deadline` equal to `next_state`, `actor` = `provider`, and a `timestamp` not earlier than the
   Result's `timestamp`.
2. If `next_state.status` is `CLOSED`, the Provider MUST also publish the closing Thing revision,
   with `closed_at` equal to that State's `timestamp`.
3. The Client endpoint MUST verify that the anchored State matches the Result.

### 9.6 Persistence

The complete Result is persistent at the Provider and at the Client endpoint. It is the only
persistent artifact of a Live Line. It MUST NOT embed or reference recordings, transcripts or any
other Line content.

### 9.7 Signatures and legal effect

The signatures of a Result give integrity and attribution to the provider key and to the Thing-key
bound through Redemption. They are not qualified electronic signatures under eIDAS. Any legal
effect is outside LP 0.1 and requires legal assessment (`02_Uuring/Regulatsioon.md` §5).

### 9.8 Relation to transaction receipts

Compared with a transaction receipt such as the co-signed receipt of PAP (§13), a Result carries
the agreed outcome content and is an input to the Thing's State machine. This describes its role in
LP 0.1; co-signing itself is prior art, and no novelty is claimed for it.

## 10. Revocation and Expiry

1. **Grant expiry.** At `redeem_by` an unredeemed Grant expires and S is deleted (§5.4). After
   `exp`: no new Live Line; an active Line ends; both parties delete `line_salt`, `PRK_line`, the
   keys derived from it and any remaining nonce-replay sets (§7.3); rendezvous envelopes lapse after
   `RDV_TTL`.
2. **Grant revocation.** The Provider MAY revoke a Grant at any time (`REVOKED`). Revocation takes
   effect immediately for Redemption and new Lines. An active Line under the Grant MUST be closed
   within `REVOCATION_CLOSE_MAX` by a signed `bye` with reason `GRANT_REVOKED` on `lyne-control`,
   followed by teardown. A Client endpoint MUST treat that `bye` as final.
3. **Epoch.** Each Thing has an epoch, starting at 0. Incrementing the epoch revokes every Grant of
   that Thing with a lower `epoch`; because `epoch` enters the rendezvous derivation, their
   rendezvous addresses also stop matching.
4. **Binding revocation (device loss or compromise).** The Provider MAY revoke the Binding of a
   Thing: it increments the epoch and records `revoked_at`. Afterwards requests and signatures by
   the old Thing-key are rejected (`KEY_MISMATCH`). A new Grant, delivered through the Provider's
   own relationship with the Client, allows a new Binding.
5. **Thing closure.** Closing a Thing (§3.2 rule 3) revokes all its Grants. The Provider MAY keep
   serving the final Thing, State chain and Results, read-only, to the bound Client for its
   retention period.
6. **Clocks.** The Provider's clock is authoritative for validity decisions. `MAX_CLOCK_SKEW` is
   tolerated only for `not_before` and for freshness checks; the Provider never extends `redeem_by`
   or `exp` by skew tolerance (fail-closed). A Client endpoint MUST NOT start a Line after `exp` by
   its own clock.
7. **Replay summary.** Grant: single `ISSUED` → `REDEEMED` compare-and-set inside a bearer phase of
   at most 15 minutes. Challenge: single use within `CHALLENGE_TTL`. Signal envelopes: a
   per-direction nonce-replay set for the active Line (§7.3). Signal messages: `seq`, `sent_at`,
   bucketed `addr` and direction-bound keys (a reflected envelope fails). Thing endpoint requests:
   RFC 9421 `created` and a replay cache. State: `version` and `prev_state_hash`. Result: one
   complete Result per (`grant_id`, `line_seq`). Lines: atomic use accounting per `line_seq`.
8. **Provider key compromise.** LP 0.1 has no transparent Provider key rotation and no compromise
   signalling (§12). When a provider key is compromised or retired, the Provider MUST stop using it
   and MUST freeze or revoke every affected Thing relationship: it issues no new Grant, accepts no
   Redemption, State proposal or Result for those Things, and ends their active Lines. A Client
   endpoint never accepts another provider key for an existing `thing_id` (§3.2 rule 5). Continuing
   the relationship under a new provider key requires a newly established trusted relationship: a
   new Thing, whose Grant the Provider delivers through its own relationship with the Client.

## 11. Security / Threat Model

The threat analysis is in `Threat_model.md`: 18 mandatory threats and 4 additional ones, each with
threat, impact, mitigation and residual risk. The resulting properties of LP 0.1:

1. Authority is explicit and bounded: every Live Line runs under a Provider-signed Grant with a
   purpose, channels, a time window and a number of uses, enforced by the Provider.
2. Possession of a link is authority only during a bearer phase of at most 15 minutes and only
   until the first Redemption; afterwards authority is bound to one Thing-key, and S is deleted.
3. Media are end-to-end protected by DTLS-SRTP, and the DTLS fingerprints are authenticated by LYNE
   signatures, so runtime components cannot insert themselves.
4. Communication content is never persistent anywhere; the persistent data are Thing, State,
   Result and content-free audit records (§15.3).
5. Client identities are separate per Thing at the Client side; the Provider can still relate the
   Things of one client through its own knowledge.
6. Residual risks that LP 0.1 does not remove: phishing at first contact, provider compromise
   without key rotation (§10 item 8), recording by participants, and network metadata visible to
   runtime operators.

## 12. Non-goals

LP 0.1 does not define or provide:

1. Inboxes, message objects, conversation history, chat widgets or contact forms.
2. A path for unknown senders, directories, search, or public or persistent addresses.
3. Client accounts, profiles, contact lists, groups or multi-party Lines.
4. Location or presence outside an active Line.
5. Content storage, recording, transcription or server-side summaries.
6. Delegation chains, agent marketplaces, agent discovery, autonomous negotiation or recursive
   mandates (§14).
7. New or custom cryptography; LP 0.1 uses only the profile of §2.6.
8. Qualified electronic signatures.
9. Client multi-device synchronization or key backup.
10. A push or notification channel.
11. Provider key rotation or compromise signalling; a compromise freezes or revokes the affected
    Thing relationships (§10 item 8).
12. Recovery, export or backup of capability secrets (S, `line_salt`, `PRK_line`); they are lost with
    the page or process that holds them, and the Provider issues a new Grant if needed (§5.4).
13. Transfer or forwarding of a Line, a Grant or a Binding to another party.
14. An emergency or legally mandated communication channel. LP 0.1 does not replace such channels
    and places no condition on them.

## 14. Endpoint Neutrality

1. An endpoint MAY be operated by a human, by an AI agent authorized by a human, by a Provider
   software agent, or by an autonomous software agent acting under explicit authority from the
   party it represents.
2. LP 0.1 MUST NOT require that either endpoint is a human. LP 0.1 defines no field and no step that
   distinguishes human from software operation; the roles are `provider` and `client`.
3. The Grant is the authority boundary for every endpoint. An endpoint, whether operated by a human
   or by software, MUST NOT act beyond the Grant, widen `purpose`, widen `channels`, extend `exp`,
   increase `max_uses`, or delegate authority. Delegation includes exporting or sharing a
   Thing-key and issuing any derived credential. LP 0.1 defines no delegation.
4. A Client that wants software to act for it chooses that software as its endpoint: the software
   redeems the Grant and holds the Thing-key. This is a choice of endpoint, not delegation.
5. The non-persistence rule (§8.5) applies equally to software endpoints: an agent MUST NOT persist
   Line content, which is transient for the duration of the Line; the Result is the only persistent
   artifact.
6. Not in LP 0.1: delegation chains, agent marketplaces, agent discovery, autonomous negotiation,
   recursive mandates.
7. Agent-initiated, bounded communication is already addressed by A2R (§4.4 of that draft) and PAP.
   Endpoint neutrality in LP 0.1 is a compatibility requirement, not a claim of novelty.

## 15. Protocol Lifecycle

### 15.1 Sequence

1. **Create.** The Provider creates the Thing (`version` 1) and State `version` 1 (`OPEN` or
   `WAITING`), both signed.
2. **Authorize.** The Provider issues a Grant for the Thing and delivers the link or QR code in its
   own context. Authority is now available; the bearer phase lasts at most 15 minutes.
3. **Redeem.** The Client endpoint takes S from the fragment and removes it, fetches and verifies
   the Grant, creates or reuses its Thing-key and redeems (§6). The Provider records the Binding;
   the Client receives Thing, State and `line_salt`; both parties replace S with `PRK_line`.
4. **Observe.** The Client reads State through the Thing endpoint whenever it opens the Thing.
   Either party proposes `OPEN` / `WAITING` transitions within its rights (§4.3).
5. **Meet.** When both endpoints are present, one sends a signed offer through the Rendezvous
   Service. The Provider enforces the Grant and consumes one use; the DTLS-SRTP Line opens (LIVE).
6. **Conclude.** A party proposes a Result on `lyne-control`; the other countersigns or declines;
   the Line ends (RESULT).
7. **Anchor.** The Provider appends the anchored State (§9.5). If `next_state.status` is `CLOSED`,
   it also publishes the closing Thing revision (CLOSED).
8. **Expire.** At `exp` both parties delete `line_salt`, `PRK_line` and the keys derived from it.
   Audit records keep metadata only. Thing, State and Results remain persistent.

### 15.2 Conceptual lifecycle mapping

| Conceptual phase | Representation in LP 0.1 | Persistent |
|---|---|---|
| OPEN | State `status` = `OPEN` | persistent (State) |
| WAITING | State `status` = `WAITING` with `waiting_on` | persistent (State) |
| Authority available | Grant `ISSUED` before `redeem_by`, or `REDEEMED` with uses remaining inside [`not_before`, `exp`) | the signed Grant is persistent in the Provider's audit |
| LIVE (UI label "LYNE") | Live Line in progress under a `REDEEMED` Grant | transient |
| RESULT | Result proposal and countersignature; the complete Result | proposal: retained until RESULT_WINDOW ends; complete Result: persistent |
| CLOSED | State `status` = `CLOSED` and Thing `closed_at` | persistent |

## Appendix A. HTTP binding (informative)

Paths are relative to the `aud` origin, except the Rendezvous Service, whose URL is returned in the
Redemption response.

| Operation | Request | Authentication | Response |
|---|---|---|---|
| FetchGrant | `GET /l/{grant_id}` | none (bearer phase; S stays in the fragment) | Grant |
| Challenge | `POST /l/{grant_id}/challenge` | none | `challenge`, expiry |
| Redeem | `POST /l/{grant_id}/redeem` with the Redemption statement | statement signature and `secret_proof` | Receipt, Thing, State, Results, `line_salt`, Rendezvous URL, optional TURN credentials |
| GetThing | `GET /t/{thing_id}` | RFC 9421, Thing-key | Thing, latest State, Results, `uses_remaining`, and `pending_result` while a Provider proposal is open |
| ProposeState | `POST /t/{thing_id}/state` with a Client-signed State | RFC 9421, Thing-key | Accepted State, or `STATE_CONFLICT` with the current State |
| SubmitResult | `POST /t/{thing_id}/result` with either the Client's countersignature of `pending_result` or a Client proposal carrying only `client_thing_sig` | RFC 9421, Thing-key | Complete Result and anchored State; a pending decision; or `RESULT_UNSIGNED` |
| Rendezvous put | `POST {rdv}/r/{addr}` with an envelope | none | accepted |
| Rendezvous get | `GET {rdv}/r/{addr}` | none | Envelopes younger than `RDV_TTL` |

The Client endpoint is always the HTTP requester; the Provider never calls the Client over HTTP
(§6.5 rule 1). Rendezvous paths use the direction-specific `addr` of §7.2.
